# Display through the OWC TB5 hub — 2026-09-20

USB on the hub works. The monitor does not. This is the live state on
`linux-aurora` `7.1.12-2.5-1-ARCH` (`2439016d`) + the two USB4 patches
already in this repo.

## What is up

- Hub authorized on USB4, 2 lanes × 20 Gb/s (40 Gb/s).
- Host port: Type-C **Left Back** (`port1`, CD321x `0-0038`, ACIO `701ac0000`).
- Partner `usb_mode=usb2 usb3 usb4`. Both DP alt-mode (`port1.0` SVID `ff01`)
  and TBT alt-mode (`port1.1` SVID `8087`) read `active=yes`; USB4 won
  because patch 0001 prefers `USB4_CONNECTION` over `DP_CONNECTION`.
- Keychron Q4 enumerates on hub USB-A (`3434:0140`).
- Hyprland only sees `eDP-1` 3456×2160@120.

## What is not up

DRM connectors besides the panel are all disconnected, no EDIDs:

| Connector   | Meaning                         | Status       |
| ----------- | ------------------------------- | ------------ |
| `eDP-1`     | internal panel                  | connected    |
| `HDMI-A-1`  | SoC dp2hdmi (no HDMI jack on this MBP) | disconnected |
| `USB-1/2/3` | USB-C DP alt-mode               | disconnected |

Kernel did try a USB4 DisplayPort tunnel, then tore it down:

```
thunderbolt-apple-nhi 701f00000.nhi: 0:5 <-> 1:19 (DP): not active, tearing down
```

`0:5` is host DP IN, `1:19` is the hub DP OUT (the hub's HDMI/DP converter,
not a downstream USB4 device — `usb4_port3/5/7` are all `link=none`).

Twelve seconds after path setup, software CM decided the pair was inactive
(no HPD on the DP OUT, or DP IN never became ready) and ripped the tunnel
down.

## Adapter on the hub

USB tree has `06cb:7100 Synaptics VMM7100` on the hub USB 2.0 hub
(`1-1.2`), interfaces HID (`03`) + Billboard (`11`). That is a USB-C
DP-to-HDMI retimer's USB side, not a pixel path.

If that dongle is in a USB-only port of the hub, video cannot work even
with a finished DP-tunnel stack. The hub's **HDMI 2.1 jack** is the DP OUT
at `1:19` and is the port that should light up once tunneling is real.

## What the warning noise is not

- `device links to tunneled native ports are missing!` — Intel Apple Mac
  (x86) resume links. Harmless here.
- `PCIe-C tunnel disabled: m1n1 handoff is not initialized` — needed for
  eGPU/NVMe enclosures, **not** for HDMI. `apple,pciec-preinit-status`
  is unset; m1n1 1.6.1 never did the PCIe-C preinit. Separate later.

## Two display paths (do not mix on the hub port)

1. **DP alt-mode on a free Mac USB-C port**
   Plug the USB-C HDMI adapter into Left Front or Right, not into the hub.
   `dcpext1` (`315c00000.dcp`) is `apple,connector-type = "USB-C"` with
   typec-routes. Experimental Asahi/Aurora DPTX; does not need USB4 DP
   tunnels. Must not steal the hub port (that is why 0001 exists).

2. **DP tunnel through the hub (the goal)**
   HDMI in the hub HDMI jack (or a TB downstream that actually does DP).
   Architecture already drawn in `drivers/thunderbolt/apple.c`:

   `dcpext → display crossbar → USB4 DP IN adapter → tunnel → hub DP OUT`

   Aurora implements PCIe-C tunnel callbacks on the NHI
   (`pci_tunnel_pre/post_activate`). There are **no** equivalent DP
   callbacks. Software CM will build a DP tunnel; DPTX is never routed
   onto `0:5`, so HPD never sticks and the tunnel dies.

`dcpext0` (`289c00000.dcp`) is labelled HDMI-A with `hdmi-hpd-gpios` /
`dp2hdmi-pwren-gpios`. This chassis has no HDMI jack; that connector
staying disconnected is expected.

Boot also logged:

```
platform 315c00000.dcp: deferred probe pending: apple-dcp:
  /soc/dcp@315c00000/typec-routes/route@0: failed to get display crossbar
```

`315c00000.dcp` later shows as bound with DPTX services. Still a
crossbar-routing smell for USB-C DP.

1. Confirm HPD: HDMI in the **hub HDMI** jack, thunderbolt dyndbg on,

2. Wire DPTX / display crossbar to USB4 DP IN (`0:5` on this port) when

3. Keep patch 0001 (USB4 before native DP on CD321x). Native DP alt-mode
   on the hub port would kill ACIO again.

Do not treat a USB-C HDMI dongle on a hub USB-C/USB-A port as a display
test. That is billboard USB, not DP.
